# Implementation notes

## Lobby and lobby rules (how it works)

- The game uses Facepunch.Steamworks (interop `Fivemid.FiveSteam.dll`). The interop has no `event` members, so the static events of `SteamMatchmaking` are subscribed with the `add_OnLobby...` methods
  (`OnLobbyEntered`, `OnLobbyDataChanged`, `OnLobbyMember{DataChanged,Joined,Leave,Disconnected,Kicked,Banned}`), next to the game's own subscriptions. Steam starts after the plugins load, so the runner tick subscribes once `SteamClient.IsValid`.
- Steam sends nothing when the local player leaves a lobby, so the 4 Hz tick also checks `Lobby.MemberCount` and the owner. `Lobby.Members` is an IL2CPP `IEnumerable<Friend>`, enumerated with `GetEnumerator/MoveNext`.
- The match starts in `GameState.StartGame` (host directly, clients through `StartGameRPC`), which invokes the game's `onStartGame` event: that is where rules freeze (`Match.Started`; a postfix on `StartGame` is the fallback, only the first call per match counts). The GameState is **not** destroyed or disabled when a match ends (its `OnDisable` only runs when the game quits): back to menu, disconnect and leaving the lobby all call `GameState.FullReset` (log line "Game State Reset."), so a postfix there unfreezes the rules (`Match.Ended`) and raises `Match.Reset`. `FullReset` invokes the game's `onReset` field too, but a handler added to that field was not called in testing, so the postfix is used.
- `Match` events: ModCore adds its handlers to the game's own `GameState` Action fields (`onIslandSpawned, onStartGame, onEnterPhase, onSyncPhase, onEndGame, onRejoin`) in a postfix on `GameState.Awake`, next to the game's handlers (Delegate.Combine). `TurnPhase.Enter` sets `GameState.TurnPhase` before it invokes `onEnterPhase`, so the phase is read there by comparing it with `startPhase` ... `winPhase`.
- Rule data: lobby data `modcore.rule.<key>` ("1"/"0" for toggles, invariant integers for numbers). Member data `modcore.mods` is `v1;<id>|<name>|<version>|<key>,<key>;...`.

## Civilizations

- `Technologies.TechTree(civilization)` uses `First(...)` and throws for an unknown civilization: a prefix returns the registered tree provider's tree.
- `PlayerSkins.Clone()` is `new PlayerSkins(civilization, skinRegistry)` and the Rules screen calls it in `OnEnable`; without a hook it threw for a mod civilization and the screen showed no tree and the wrong biome.
- `PlayerSkins.Civilization`'s setter switches over 0..4 and throws otherwise: a prefix sets the borrowed built-in civilization first, then stores the real number.
- A registered civilization without a tree provider (or with one that returns null) gets the tree of its `skinsLike` civilization: the original `First(...)` would throw.
- Picking a civilization for play: clicking the castle on the match-start screen runs `Player.NextCivilization` (host side, clients send `NextCivilizationRPC`), which steps through the player's unlocked civilizations (`Player.Inventory.UnlockedCivilizations`, from the Steam inventory) and wraps around. `NextCivilizationHook` (a prefix) adds the registered civilizations to the end of that cycle: after the last unlocked civilization the first registered one is set, then the next one, and after the last registered one the game's own wrap-around runs. The `PlayerSkins` constructor throws for unknown numbers, so the skins are built for the `skinsLike` civilization and the real number is stored afterwards. **Do not replace or patch the player's inventory.** An earlier version did (a postfix on `PlayerInventory.FromSteamworks`, then writing `PlayerInventory.FALLBACK`) and the lobby stopped building: `Player.NetworkStart` also picks the random starting civilization out of that same array (`NextSample<Civilization>`), and it threw `IndexOutOfRangeException`, so no player was spawned. Patching the tiny `UnlockedCivilizations` getter is no better: IL2CPP shares identical getters and hooking it crashed the game at startup.
- The ids come from a hash of the key, **5..127**, so every machine computes the same number. The range is the network format: `PlayerSkinsSerialization.WritePlayerSkins` writes the civilization as one byte and `ReadPlayerSkins` (and the stream reader, the lambda `<OnEnable>b__5_1`) read it with `ReadSByte()` and build `new PlayerSkins(civ, registry)`, whose constructor throws for anything outside 0..4. An earlier version used 1000+ and a friend's game received 60. Constructors cannot be patched under IL2CPP ("Failed to init IL2CPP patch backend"), so the two readers are replaced instead (`PlayerSkinsLookHooks`): the registered civilization gets the `skinsLike` look and keeps its number, an unknown number becomes civilization 0 and logs once.
- Visual lookups: `PlayerSkins.Get*Prefab` call `SkinRegistry.GetSkinVariant(defaultPrefab, null biome, civilization, "")`, a dictionary lookup that returns the default prefab when the key is missing, so a mod civilization silently looked European. While one of the five getters runs, the `civilization` field is swapped to the `skinsLike` number (prefix) and restored (finalizer, which also runs when the original throws). A model set in `civ.Skins` is returned instead by the prefix (`CivilizationSkinHooks`).
- Inlined lookups: the compiler inlined `Technologies.TechTree(civ)` (`First(trees, t => t.civilization == civ)`) into `Statistics.get_TechTree` and `Statistics.IsTechnologyLearnable`, so patching `Technologies.TechTree` is not enough. `TechnologyInterface.OnEnable` (the research window) and `TechTreeInterface.Update` (every frame) call them. `StatisticsTechTreeHook` replaces the getter for registered civilizations; `StatisticsLearnableHook` reproduces `IsTechnologyLearnable` (not learnt; demo: only `UNLOCK_STORAGE`; no dependencies or one learnt dependency). Do **not** patch tiny getters such as `PlayerSkins.get_Civilization`: IL2CPP shares identical native getters.
- AI: `AIPlay.SampleBuildOrder` filters the 15 embedded build orders by exact civilization and throws `No build order matching civilization=N`; a prefix swaps the argument for `skinsLike`.
- Lobby safety: each client publishes `modcore.civs` (`v1` plus `key=id` pairs) in its member data. The castle click only offers civilizations everybody has, and `CivilizationGuard` (host, in the lobby, once a second and on member changes) moves a player off a civilization a member lacks, because that member's game would throw on the number.
- Text: the name key is `civilization.{value}.name` in the table `StructuredTextStaticReferences.instance.localizationStringTable`; `CivilizationText` adds missing entries once a second (tables are per language).
- Tech trees (`CloneTree`, tested): `Technologies.TechTree(civ)` is looked up on every call, so a provider must return one cached instance; the copy is `Object.Instantiate` of the built-in `TechTree` with `HideAndDontSave`. `TechTree.Slots` is an array of structs (technology, `position` int2, `links`): copy a slot out, change it, write it back. The grid uses even x (0, 2, 4, 6, 8; odd values are link ports) and y 0..4 and two slots on one cell are drawn on top of each other. `TechTreeInterface.Populate` builds the window from the copy, so a moved slot shows immediately.
- `DumpGameData` (config) writes `BepInEx/ModCore-game-data.txt` and `ModCore-sprites.txt`; it is read-only and off by default.
- Debugging tip: `LogOutput.log` only has the first line of an exception; the game's `Player.log` has the whole stack trace, which is how each of the hooks above was found.

## Event frequency (measured)

The game writes its own lobby and member data several times a second (a solo match with AIs produced over 100 `OnLobbyDataChanged` / `OnLobbyMemberDataChanged` events in a few minutes).
So `OnDataChanged` only re-evaluates the rules, and `Lobby.Changed` is raised for membership and owner changes only. Set `[Debug] LogLobbyEvents = true` in `DiceModders.ModCore.cfg`
to trace the events; the data events are summarised as one counter line per lobby/match phase.

## Players and messages

- `Player.AI` (`Nullable<AIState>`, a struct with two array fields) comes back as garbage through the interop. `MatchPlayer.Difficulty/Strategy` read the field directly: `Player.ai` at 0xD0 is a `NetworkedVar<Opt<AIState>>`, its value at +0x38 (`hasValue` +0x38, `Difficulty` +0x40, `Strategy` +0x44; from `Player.get_AI`, v1.0.4). Values outside the enum range are treated as a changed layout and reported as null.
- The AI picks its strategy and build order when the Start phase ends; before that the value is the default.
- With fewer than two humans the game sets `LobbySettings.timerSpeed` to UNLIMITED at match start.
- `Log.AddMessage(StructuredText)` only works on the server. `GameText` builds the `StructuredText` from `FormattableStringFactory.Create("{0}{1}..", args)`: `Il2CppSystem.String` holes become text with `{r.gold}`-style tokens parsed, `Player` holes become coloured names.

## Own building models

- `CivilizationSkins.BuildingModel`: on the first `GetBuildingVisualPrefab` lookup for the type, the look-alike prefab (`__result`) is copied with `Object.Instantiate` under an inactive `DontDestroyOnLoad` object (the copy never wakes up). Body MeshFilters are named `<building>-<civ>-mesh_LOD<n>` under `Visual` and `Damaged Visual`; some prefabs hold two LOD groups (`Castle Viking`: europe + viking), so only the group of the look-alike civilization is filled and the others get an empty mesh (two filled groups z-fight). `flag-big` is moved. Materials stay. No `BuildingVisual.Apply` patch is needed: the game instantiates the copy everywhere.
- 2D pictures: `BuildingVisual.Icon(color)` returns `icons[color.Index]` with no fallback, and every UI place (lobby card, player summary, scoreboard, end screen, build menu, Rules screen, text icons) calls it. The copy gets its own 12-entry array (checked length, no nulls); the original prefab is never touched.
- `Mesh.RecalculateNormals` is stripped in this build, so `Tools.Meshes` computes normals itself.
